# ADR-001: r2d2-sqlite for SQLite Connection Pooling

**Date:** 2026-05-15  
**Status:** Accepted  
**Author:** Architecture Plan

## Context

The prototype used a "pool" that was actually a path holder — every query, schema fetch, and row edit called `Connection::open()` creating a fresh connection. For a production tool, we need actual connection pooling that reuses connections and handles concurrent access properly.

Two options exist: `r2d2-sqlite` and `deadpool-sqlite`.

## Decision

Use `r2d2-sqlite` for SQLite connection pooling.

## Rationale

1. **Maturity:** r2d2 has been the standard Rust connection pool for years. It's well-documented with known performance characteristics.

2. **Sync API compatibility:** rusqlite's API is synchronous. r2d2 wraps sync connections with thread-based pooling, which matches naturally. deadpool-sqlite wraps rusqlite in an async API, adding a Tokio dependency that SQLite queries don't benefit from.

3. **No additional Tokio dependency for SQLite queries:** The app already uses Tokio for PostgreSQL (via deadpool-postgres) and Tauri's async runtime. Adding async wrappers around inherently sync SQLite queries is unnecessary overhead.

4. **Configuration surface:** WAL mode, busy timeout, and cache size are set at pool creation, not per-connection. r2d2's `ManageConnection` trait makes this straightforward.

## Consequences

- SQLite queries run on a thread pool (r2d2's internal pool), not on the Tokio runtime
- The Backend Systems Engineer must configure pool size appropriately (default: min 2, max 8)
- WAL mode must be enabled at pool initialization to allow concurrent reads
- Busy timeout must be set (5 seconds) to handle write contention gracefully

## Alternatives Considered

- **deadpool-sqlite:** Adds async overhead for sync operations. Requires Tokio for SQLite queries. Less mature.
- **sqlx:** Full ORM-like abstraction. Hides type metadata we need for the grid. Overkill for our use case.
- **Custom pool:** Not worth the maintenance burden. r2d2 is battle-tested.

# ADR-002: Tagged Enums for All IPC Types

**Date:** 2026-05-15  
**Status:** Accepted  
**Author:** Architecture Plan

## Context

The prototype had a serialization mismatch: `HistoryStatus` was a plain string in Rust (`"success"` or the error message) but a discriminated union in TypeScript (`{ type: "success" } | { type: "error"; message: string }`). This would cause runtime deserialization failures.

More broadly, all types crossing the IPC boundary need to serialize consistently.

## Decision

All Rust enums that cross the IPC boundary must use `#[serde(tag = "...", content = "...")]` to produce self-describing JSON objects. TypeScript types must mirror these exactly as discriminated unions.

## Rationale

1. **Self-describing JSON:** A tagged enum produces `{"type":"Text","value":"hello"}` which is unambiguous. A plain string `"success"` doesn't carry type information.

2. **TypeScript discriminated unions match naturally:** TypeScript's `type CellValue = { type: "Null" } | { type: "Text"; value: string } | ...` gives exhaustive checking and autocomplete.

3. **Future-proofing:** If we add a new variant (e.g., `Binary(Vec<u8>)`), the tagged format means old clients can deserialize the tag and handle unknown variants gracefully.

## Consequences

- Every enum crossing the IPC boundary must be tagged: `CellValue`, `HistoryStatus`, `DbType`, `ConnectionStatus`, `SslMode`
- Plain structs (not enums) don't need tags: `PgConfig`, `ConnectionInfo`, `QueryResult`, `TableInfo`, `ColumnInfo`
- TypeScript types must be kept in sync manually (no code generation in v1)

## Alternatives Considered

- **Untagged enums:** Serde can serialize enums as plain strings or numbers. These are ambiguous and can't carry data for error variants.
- **Adjacently tagged:** `#[serde(tag = "type", content = "value")]` vs `#[serde(tag = "t", content = "c")]`. Use the standard names for readability.
- **Code generation (ts-rs):** Would automate sync but adds a build step and dependency. Consider for v2.

# ADR-003: Services Layer Between Commands and Database Drivers

**Date:** 2026-05-15  
**Status:** Accepted  
**Author:** Architecture Plan

## Context

The prototype had business logic embedded directly in Tauri command handlers. This made testing difficult (commands require a Tauri context) and mixed concerns (IPC deserialization with database operations).

## Decision

Introduce a `services/` layer. Commands are thin wrappers that deserialize IPC arguments, call a service method, and serialize the result. All database interaction logic lives in services.

## Rationale

1. **Testability:** Integration tests can call services directly without Tauri. `query_service.execute(connection_id, sql)` is testable. `#[tauri::command] fn execute_query(...)` requires Tauri.

2. **Separation of concerns:** Commands handle IPC concerns (serialization, state extraction). Services handle business logic (query execution, type coercion, transaction management).

3. **Reusability:** The `export_csv` command needs to execute a query. It calls `query_service.execute()` — the same service the `execute_query` command uses. No duplication.

## Consequences

- Every command function becomes ~5-10 lines (extract state, call service, return)
- Services are tested independently in `tests/integration/`
- Service methods take explicit parameters, not Tauri State wrappers

## Alternatives Considered

- **Commands directly call database drivers:** Testable only through Tauri integration tests. Mixes concerns.
- **Repository pattern:** Overkill for this scope. Services are repositories with additional logic (type coercion, PK discovery).
